# BasketMap decisions

Status: product choices from the build brief. They are hypotheses and implementation constraints, not findings from customer research.

| Decision                                                  | Reason                                                                                                                            | Trade-off / alternative deferred                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| One store per basket                                      | The immediate job is choosing a single grocery stop.                                                                              | Splitting purchases might lower item cost but introduces multiple journeys and a larger optimization problem. |
| Whole packs with fixed specifications                     | Two 500 g packs must cost twice the defined pack price; attributes and packaging remain comparable.                               | Arbitrary quantities, whole-pack fulfillment, and substitutions need explicit additional rules.               |
| Separate complete and partial baskets                     | A missing price cannot be represented as zero. Only complete totals answer the product question.                                  | Fewer stores may qualify; partial results still expose coverage and missing items.                            |
| Price and straight-line distance remain separate          | Visitors differ in their willingness to travel.                                                                                   | No invented monetary cost of inconvenience or travel-time conversion.                                         |
| Nearest complete eligible store is the baseline           | The example difference is anchored to a named, practical alternative under the same filters.                                      | It is not savings against every shop, actual spending, or an annual projection.                               |
| Synthetic demo first                                      | Deterministic data can demonstrate interaction and arithmetic while useful observed coverage remains uncertain.                   | The demo cannot recommend real supermarkets or establish current prices.                                      |
| Snapshot registry with explicit versions                  | Cards, map, detail, persistence, sharing, and export can refer to one reproducible dataset.                                       | Updating a published version requires an explicit data release rather than silently replacing evidence.       |
| Regular in-store pack prices only                         | Channel, promotion, package, and loyalty differences can invalidate comparisons.                                                  | More source rows are excluded; unknown conditions remain unresolved.                                          |
| Newest eligible observation; unresolved same-day conflict | Recency is relevant and choosing the lowest conflicting value would bias the ranking.                                             | A recent disagreement can make a basket incomplete even when older records exist.                             |
| Client-only state and tools                               | A static prototype requires no account, price-service uptime, or backend. Local import can validate files without uploading them. | No cross-device sync, shared private imports, or aggregate visitor analytics.                                 |
| Selectable coordinate fallback                            | Map tiles should enrich the result rather than prevent store selection.                                                           | A coordinate plot has no streets or route information and must say so.                                        |
| Original frontend and engine                              | The scoped React/TypeScript application is small enough to implement directly.                                                    | Reusing a server-heavy app would add migration and hosting scope.                                             |

[GroceryGuru](https://github.com/LuckyLuciano97/GroceryGuru) inspired full-basket ranking and separate incomplete results. Its repository identifies Apache-2.0. BasketMap's application and synthetic fixture are original work; no GroceryGuru source code, retailer logos, receipt images, or product photographs are copied.

The observed-release gate is a product assumption: at least two nearby physical branches with a complete overlap of six clearly comparable items under the selected eligibility and age rules. A failed bounded import should yield a coverage explanation while preserving the working demo. A 30-day age cutoff is a chosen policy, not a guarantee that a price is still valid.
